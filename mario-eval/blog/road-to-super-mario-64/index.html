The road to Super Mario 64

2026-11-14

The eval is named for Super Mario 64, and SM64 is where it is headed: a game whose engine is famously unoptimized as shipped (built without compiler optimization, with debug code left in) and whose decompilation has made it the best-studied N64 codebase there is. Kaze's rewrite of the whole source shows how far it can be pushed; his video on walls shows the trap, an optimization that also quietly removes glitches speedrunners rely on.

Why it isn't the first workload

The n64decomp/sm64 project is code only. Building it extracts textures, models, sounds and music from a ROM you supply, and this project does not distribute Nintendo's ROM or assets. Rather than block on that, the whole pipeline was built and calibrated on Pip's Garden, an original game, and SM64 plugs into it.

What carries over unchanged

  • The emulator build, its instrumentation and the logical-frame protocol.
  • The grader: trusted rebuild, gates, metrics, profiles and reward.
  • The agent container, the egress proxy and the run supervisor.
  • The calibration discipline.

What is already in place

sm64/setup.sh takes your ROM, checks it is the US release by SHA-1, checks out the decompilation at a pinned commit and builds the matching baseline. The decompilation directory, and everything extracted from the ROM, is kept out of git.

The five remaining steps

  1. Harness calls in the game loop. SM64 reads the controllers once per frame through the PIF, synchronously, which is exactly what the harness needs: that read becomes mev_read_pad(), and mev_end_frame() goes after the frame's graphics task completes.
  2. An unthrottled build. The game loop waits for the video retrace; a benchmark build skips the wait so frame cost is pure work, the same approach the community's profiling builds take.
  3. An observation record. Mario's position, velocity, action, health, coins and stars, the camera, the RNG seed and the active objects, compared bit for bit. This is what turns "don't change the game" into something a grader can check, and it is why an SM64 wall-collision rewrite that loses a glitch would be caught.
  4. Routes. Controller routes through several courses, each starting from a replayed path out of the file select screen rather than an emulator savestate, because a savestate pins one build's memory layout and an optimized build won't have it.
  5. Calibration. The unchanged rebuild must score zero; known-good patches (IEEE-preserving -O2, Create Dirty Exclusive, memory savings) positive; shortcuts −1.

Each of these needs the ROM to build and test, so none of them ships before it has been verified.

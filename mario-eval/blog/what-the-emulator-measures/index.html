What the emulator can and can't measure

2026-11-14

An RLVR reward is only as good as the thing that produces it. For Mario Eval that is ares, so before choosing the reward profiles I read the parts of its N64 core that decide what a cost is.

Modelled

  • CPU timing and both caches. With the interpreter (the recompiler bypasses the cache model), every instruction fetch goes through a 16 KB, 32-byte-line instruction cache and every load and store through an 8 KB, 16-byte-line write-back data cache. A miss stalls the CPU for a fixed number of cycles and moves a line over the bus.
  • The CACHE instruction. All the data-cache operations are implemented, including Create Dirty Exclusive, which marks a line valid and dirty without reading RDRAM. This is the instruction Kaze covers in his CACHE video; in ares it really does save the fill.
  • RSP timing. The vector coprocessor's busy and halted cycles are counted.
  • Bus traffic by device. In homebrew mode ares counts bytes read and written by the CPU's I-cache, D-cache and uncached accesses, and by SP, DP, PI, SI, VI and AI DMA.

Not modelled

  • RDP rasterization time. ares hands the RDP's commands to paraLLEl-RDP, which draws them correctly but reports completion immediately. On a console, a frame full of large textured triangles can be RDP-bound; here it never is.
  • Bus contention. A cache miss costs the same whether or not the RSP and RDP are hammering RDRAM at that moment. On a console, much of the cost of memory traffic is that everyone else has to wait for it.

What that means for the profiles

The four profiles were chosen to be measurable in this model:

  • speed is CPU time per frame, unthrottled, which includes every cache stall and any time the CPU spends waiting on the RSP. It does not include RDP time, so making the RDP's job easier is not rewarded.
  • rsp is RSP busy cycles.
  • traffic counts every byte moved over the bus. Because contention isn't modelled, a reduction is counted even when it would not have stalled anything; this is the profile that best stands in for "less pressure on the shared bus", which the model can't charge for directly.
  • memory counts distinct RDRAM lines touched after the boot loader hands over, so the IPL3 clearing all of RAM is not charged to the game, while a buffer the game clears once at startup is.

"Frame time on a real console" is deliberately not one of them. It would need the RDP and the bus modelled, or measured.

Deterministic, so small numbers are real

The same ROM run twice gives identical counters, so a 3% change is a 3% change. That is useful and occasionally surprising: in calibration, reassociating one matrix product (same math, different rounding) moved RDRAM traffic up to 8% on one route, and replacing sinf with a table made the CPU faster but raised I-cache traffic by up to 30%, because the code moved and started colliding with other hot code in a direct-mapped cache. Kaze calls this the performance lottery in his audio optimization video. The grader doesn't hide it; a traffic-tasked agent has to manage layout as well as algorithms.

Closing the gap

The honest claim today is "cheaper on the ares N64 model". Turning that into "cheaper on an N64" needs hardware runs: the same ROMs on a console with a flash cartridge, timed with the CPU's Count register around the same harness calls, for the calibration patches and for the best submissions. If the rankings agree, the model is good enough for that profile; where they don't (anything RDP-bound will be the first place), the profile needs a better model or a hardware-in-the-loop grade.

What the emulator measures (and how we closed the RDP gap)

ILYAAS KAPADIA · 2026-11-16

An RLVR reward is only as honest as the hardware model underneath it. Stock N64 emulators optimize for 60 Hz desktop playback rather than cycle attribution: dynamic recompilers skip cache simulation, and fast HLE/Vulkan plugins complete RDP draws instantaneously. Before wiring the leaderboard profiles, we audited ares's N64 core and added 0001-mario-eval-instrumentation.patch so CPU, RSP, RDP, and RDRAM costs are all first-class signals.

Modelled inside n64run

  • VR4300 CPU timing and direct-mapped caches. Running ares's pure interpreter sends every instruction fetch through the 16 KB (32-byte line) direct-mapped I-cache and every load/store through the 8 KB (16-byte line) write-back D-cache. Misses stall the CPU and transfer exact cache lines over RDRAM.
  • CACHE 0x0d (Create Dirty Exclusive) & hardware cache invariants. Every VR4300 CACHE opcode is active. Marking a 16-byte aligned scratch line dirty-exclusive before overwriting a 64-byte Mtx or vertex buffer genuinely eliminates the wasted RDRAM line fill, matching Kaze Emanuar's CACHE hardware benchmarks. In v3.1, n64run also enforces real VR4300 cache-safety invariants: non-16-byte-aligned CACHE 0x0d ops, uncached KSEG1 accesses aliasing dirty KSEG0 D-cache lines, and SP/DP DMA reads overlapping dirty CPU D-cache lines are all detected directly.
  • RSP vector & scalar cycles (split by task type). Non-halted RSP cycles are counted across both M_GFXTASK geometry/lighting Display Lists (rsp_gfx_cycles) and M_AUDTASK ADPCM audio synthesis (rsp_aud_cycles).
  • Deterministic 62.5 MHz RDP (gclk) cycle, early-Z & 4-bank RDRAM row-miss model. Alongside paraLLEl-RDP's exact pixel rendering, our RDP command profiler models 1-cycle vs 2-cycle/copy/fill raster throughput, Z-buffer read/compare/write (with early-Z write rejection on occluded spans) and blender read-modify-write memory penalties, 4-bank × 2 KB RDRAM open-row page misses (24 gclk/switch), TMEM load stalls (LoadBlock, LoadTile, LoadTLUT), DPPipeSync / DPLoadSync / DPTileSync pipeline flushes, and symmetric MI/RI RDRAM burst turnarounds. Switching opaque layers from G_RM_AA_ZB_OPA_SURF to G_RM_RA_ZB_OPA_SURF or culling off-screen skybox tiles directly drops rdp_busy, rdp_effective_cycles, and DP Draw bus traffic.
  • Per-device RDRAM traffic & 4 MB cacheline footprint. Every RDRAM transfer is attributed to its bus master (VR4300 ICache, VR4300 DCache, VR4300 Uncached, SP DMA, PI DMA, SI DMA, DP DMA, and DP Draw), and a 16-byte line bitmap reset at the game's entry point measures exact post-IPL3 RAM footprint against the 4,194,304-byte limit.

How the seven profiles map to hardware

  • console (headline) takes the per-frame bottleneck max(CPU_ms, RSP_ms, RDP_ms, RDRAM_ms) across the suite within 4 MB RAM. A course stalled on VR4300 collision code and a scene stalled on RDP fillrate must both get faster to move the headline FPS.
  • stutter tracks the 99th-percentile per-frame console bottleneck (est_console_p99_ms) so rare frame-time spikes cannot hide behind a fast mean.
  • speed isolates VR4300 effective cycles (93.75 MHz) including I/D-cache miss and bus contention stalls.
  • rdp isolates 62.5 MHz RDP raster, Z/blend, TMEM, and sync cycles.
  • rsp isolates RSP microcode busy cycles.
  • traffic sums RDRAM bytes across all bus masters — standing in directly for shared Rambus bandwidth pressure.
  • memory counts distinct 16-byte RDRAM cachelines ever touched after boot.

Deterministic, so cache-layout effects are real

Two runs of the same ROM produce identical cycle, cache, RDP, and RDRAM counts down to the last tick. That makes direct-mapped cache collisions immediately visible. Even a 96-byte shift in code size can push hot globals into an 8 KB D-cache alias with the stack/heap; on vanilla Super Mario 64, rendering_graph_node.o and math_util.o sit almost exactly 63 × 16 KB apart in sm64.us.map, evicting each other on every scene-graph node. Kaze calls this the performance lottery; controlling sm64.ld section layout turns luck into deterministic engineering.

What still separates emulation from a physical deck

While individual CPU cache stalls, RSP cycles, RDP fill/TMEM/page-miss cycles, per-master RDRAM byte counts, and bus-coupled CPU & RDP RDRAM contention stalls are all modelled deterministically, exact sub-scanline Rambus arbiter interleaving between concurrent DMA bursts remains an analytical approximation rather than gate-level RTL. Validating top calibration rungs and frontier agent checkpoints on a retail NUS-CPU deck via flashcart remains the ultimate ground truth.

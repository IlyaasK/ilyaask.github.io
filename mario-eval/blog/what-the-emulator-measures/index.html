What the emulator measures (and how we closed the RDP gap)

ILYAAS KAPADIA · 2026-11-16

An RLVR reward is only as honest as the hardware model underneath it. Stock N64 emulators optimize for 60 Hz desktop playback rather than cycle attribution: dynamic recompilers skip cache simulation, and fast HLE/Vulkan plugins complete RDP draws instantaneously. Before wiring the leaderboard profiles, we audited ares's N64 core and added 0001-mario-eval-instrumentation.patch so CPU, RSP, RDP, and RDRAM costs are all first-class signals.

Modelled inside n64run

  • VR4300 CPU timing and direct-mapped caches. Running ares's pure interpreter sends every instruction fetch through the 16 KB (32-byte line) direct-mapped I-cache and every load/store through the 8 KB (16-byte line) write-back D-cache. Misses stall the CPU and transfer exact cache lines over RDRAM.
  • CACHE 0x0d (Create Dirty Exclusive). Every VR4300 CACHE opcode is active. Marking a 16-byte aligned scratch line dirty-exclusive before overwriting a 64-byte Mtx or vertex buffer genuinely eliminates the wasted RDRAM line fill, matching Kaze Emanuar's CACHE hardware benchmarks.
  • RSP vector & scalar cycles. Non-halted RSP cycles are counted across both gspFast3D geometry/lighting Display Lists and rspAspMain ADPCM audio synthesis.
  • Deterministic 62.5 MHz RDP (gclk) cycle & pixel model. Alongside paraLLEl-RDP's exact pixel rendering, our RDP command profiler models 1-cycle vs 2-cycle/copy/fill raster throughput, Z-buffer read/compare/write and blender read-modify-write memory penalties, TMEM load stalls (LoadBlock, LoadTile, LoadTLUT), and DPPipeSync / DPLoadSync / DPTileSync pipeline flushes. Switching opaque layers from G_RM_AA_ZB_OPA_SURF to G_RM_RA_ZB_OPA_SURF or culling off-screen skybox tiles directly drops rdp_busy and DP Draw bus traffic.
  • Per-device RDRAM traffic & 4 MB cacheline footprint. Every RDRAM transfer is attributed to its bus master (VR4300 ICache, VR4300 DCache, VR4300 Uncached, SP DMA, PI DMA, SI DMA, DP DMA, and DP Draw), and a 16-byte line bitmap reset at the game's entry point measures exact post-IPL3 RAM footprint against the 4,194,304-byte limit.

How the six profiles map to hardware

  • console (headline) takes the per-frame bottleneck max(CPU_ms, RSP_ms, RDP_ms) across the suite within 4 MB RAM. A course stalled on VR4300 collision code and a scene stalled on RDP fillrate must both get faster to move the headline FPS.
  • speed isolates VR4300 COUNT ticks (46.875 MHz) including I/D-cache miss stalls.
  • rdp isolates 62.5 MHz RDP raster, Z/blend, TMEM, and sync cycles.
  • rsp isolates RSP microcode busy cycles.
  • traffic sums RDRAM bytes across all bus masters — standing in directly for shared Rambus bandwidth pressure.
  • memory counts distinct 16-byte RDRAM cachelines ever touched after boot.

Deterministic, so cache-layout effects are real

Two runs of the same ROM produce identical cycle, cache, RDP, and RDRAM counts down to the last tick. That makes direct-mapped cache collisions immediately visible. On Pip's Garden, deleting 208 bytes of LOD branch code shifted downstream globals into an 8 KB D-cache alias with the stack/heap, quadrupling D-cache misses from ~6,800 to ~28,700 per frame; on vanilla Super Mario 64, rendering_graph_node.o and math_util.o sit almost exactly 63 × 16 KB apart in sm64.us.map, evicting each other on every scene-graph node. Kaze calls this the performance lottery; controlling sm64.ld section layout turns luck into deterministic engineering.

What still separates emulation from a physical deck

While individual CPU cache stalls, RSP cycles, RDP fill/TMEM cycles, and per-master RDRAM byte counts are all modelled deterministically, simultaneous cycle-by-cycle Rambus arbitration stalls between overlapping CPU and RCP burst transfers are captured as aggregate bus bytes in traffic rather than dynamic wait states. Validating top calibration rungs and frontier agent checkpoints on a retail NUS-CPU deck via flashcart remains the ultimate ground truth.

Building Mario Eval

2026-11-14

Mario Eval asks a coding agent to do what N64 developers and, decades later, modders like Kaze Emanuar have spent years on: make a Nintendo 64 game cheaper to run on the console it shipped for, without changing the game. It is built as an RLVR environment, so the hard part is not the task statement but the reward: a number that goes up only when the game genuinely got cheaper and stayed the same.

Why the N64

The N64 is a good place to test optimization skill because its costs are unusual and well understood. The CPU has a 16 KB instruction cache and an 8 KB data cache, both direct-mapped, in front of 4 MB of RDRAM that the CPU, the RSP, the RDP, audio and video all share. Instruction count is a poor proxy for cost: a loop that executes more instructions can be faster if it stays in cache, moving a function can make the game slower because it now collides with another one, and storing to memory you are about to overwrite costs a read first unless you use the CACHE instruction to say otherwise. Kaze's videos on render speed, memory use and the CACHE instruction are the best tour of how much room there is, and of how often a plausible change is the wrong one.

Grader first

The tempting first step is to build the best optimized version of the game, then measure models against it. I did the opposite. A fully optimized starting point removes the accessible improvements and bakes in one person's idea of what counts. What an eval needs first is a grader that ranks known patches correctly: a real improvement scores positive, a shortcut that changes the game scores −1, and a change that trades one resource for another shows up as exactly that. Everything else (the agent container, the corpus, the site) came after calibration worked.

What is verified

A submission is a source tree. The grader rebuilds it with a pinned libdragon toolchain and runs it in ares, the accuracy-focused emulator, built from a pinned commit with a small patch that counts RDRAM lines touched and samples the CPU's program counter. ares runs the CPU interpreter here, so its models of both caches apply to every instruction, and its Create Dirty Exclusive implementation really skips the line fill.

Two design choices make the measurement honest:

  • Logical frames, not video fields. The game runs unthrottled and reports the end of each frame through a harness call. Controller input is served per logical frame. A build that is twice as fast sees the same inputs on the same frames and plays the same game; if inputs were tied to video timing, faster code would literally play a different game and the comparison would be meaningless.
  • The emulator counts, the ROM doesn't. Frame cost is the CP0 Count register as ares advances it; RSP time, bus traffic per device and RAM footprint are counted inside the emulator. A ROM can't report a better number than it earned.

Correctness is checked frame by frame against the original: the gameplay state bit for bit, the picture with a one-pixel neighbourhood tolerance, the audio by signal-to-noise ratio. The tolerances were chosen from calibration patches, not guessed: legitimate changes land orders of magnitude inside them, shortcuts orders of magnitude outside.

One objective per task

"Faster, cheaper, more efficient" is several objectives that disagree. A lookup table trades RAM for CPU time; batching trades traffic for buffer space; a code change can speed the CPU up and increase bus traffic because the new layout misses the instruction cache more. Rather than invent an exchange rate between bytes and cycles, each task names one profile (speed, rsp, traffic or memory) and the others act as budgets. Calibration shows why this matters: precomputing the terrain's heights makes the game 10% faster and fails the memory budget, because the table is 448 bytes the original didn't need. That is a real trade, not a grader bug.

Why a stand-in game

Super Mario 64 is the point, but the decompilation can only be built from a ROM dumped from a cartridge you own, and none is distributed here. So the harness was built and calibrated on Pip's Garden, an original game written for this eval: small, deterministic, and unoptimized in the ways real 1990s engines were, from -O0 builds to per-object matrix rebuilds and a software synthesizer that calls asinf for every sample. Everything about it that matters to grading (the harness contract, the logical-frame protocol, the measurements) carries over to Super Mario 64 unchanged; the road to Super Mario 64 post covers what changes.

The agent's environment

The agent works in a container with the game's source, the toolchain, the emulator and the same grader it is scored by, restricted to the public routes. mev profile gives a clock-weighted per-function profile in which cache stalls land on the instruction that caused them. The container sits on a Docker network with no route out; its only egress is a proxy that admits model-API hosts and refuses everything else, which was checked from inside the container. Held-out routes live on the host and are only used when a checkpoint is graded.

What it doesn't measure (yet)

ares does not model how long the RDP takes to draw, or contention on the memory bus between the CPU and the RCP. Those are real costs on a console, and the eval can't reward reducing them until it can measure them; the emulator post goes through what that means for the profiles and how hardware validation would close the gap.

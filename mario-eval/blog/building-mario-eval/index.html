Building Mario Eval

2026-11-14

Mario Eval asks a coding agent to do what N64 developers and, decades later, engineers like Kaze Emanuar have spent years on: make a Nintendo 64 game faster and cheaper to run on the original 4 MB console it shipped for, without changing what the player gets. Modeled on Mechanize's GBA Eval and built as a 24-hour RLVR environment, the hard part is not the prompt — it is making sure the reward goes up only when the game genuinely got faster on N64 hardware and stayed the same game.

Why the N64

The N64 is an unusually sharp test of systems optimization because its bottlenecks look nothing like modern x86 or ARM servers. The VR4300 CPU has a 16 KB instruction cache and an 8 KB data cache, both direct-mapped, sitting in front of 4 MB of unified RDRAM shared by the CPU, the 62.5 MHz RSP vector processor, the 62.5 MHz RDP rasterizer, audio, and video scanout. Instruction count is a poor proxy for speed: unrolling a loop can evict its caller from the 16 KB I-cache, two hot translation units 63 × 16 KB apart thrash every call, storing to a scratch matrix wastes a full RDRAM cache-line read unless you claim the line with CACHE 0x0d (Create Dirty Exclusive), and opaque anti-aliased surfaces pay double-read framebuffer traffic on the RDP unless switched to reduced-aliasing G_RM_RA_ZB_OPA_SURF. Kaze's videos on render speed, memory layout, collision caches, and the CACHE instruction show both how much headroom exists and how easily a textbook optimization makes real N64 hardware slower.

Grader first

The tempting first step is to hand-optimize the game and benchmark agents against your patch. I did the opposite. What an RLVR benchmark needs first is a grader that ranks known good and bad changes honestly: genuine hardware wins score positive, shortcuts that alter physics or drop geometry score −1, and optimizations that trade RAM for cycles show up cleanly against their budgets. Everything else (the 24-hour container supervisor, the 12-course SM64 suite, the leaderboard and partial Kaze reference) rests on calibration.

What is verified

A submission is a source tree — either Super Mario 64 (n64decomp/sm64, prepared locally from your own US .z64 ROM) or Pip's Garden (our self-contained 3D libdragon game that runs out of the box with zero Nintendo assets). The grader rebuilds the ROM from source, verifies that the real-time VBlank console build (PLAY=1) also compiles cleanly, and runs every public and held-out route under an instrumented build of ares (CPU interpreter mode, full direct-mapped I/D-cache simulation, RSP vector microcode cycles, deterministic 62.5 MHz RDP combiner/Z/TMEM/sync cycles, per-device RDRAM bytes, and 16-byte RDRAM footprint).

Two design choices keep the measurement honest:

  • Logical frames, not video fields. In benchmark mode the ROM runs unthrottled and signals frame completion after both RSP and RDP finish and deterministic audio subframes synthesize. Controller inputs are keyed by logical frame, so a build that runs twice as fast plays the exact same trajectory instead of desynchronizing input timing.
  • The emulator counts, the ROM doesn't. VR4300 COUNT ticks, cache misses, RSP busy cycles, 62.5 MHz RDP cycles, RDRAM bus bytes per master, and 4 MB RAM footprint are all snapshotted inside n64run on the host side. A submission cannot spoof its own cost.

Player equivalence and Hyrum's Law

On Super Mario 64, gating internal struct bytes or PRNG seeds lockstep would reject legitimate engine engineering like Kaze's distant object hibernation or reordered scene-graph culling. Instead, SM64 gates on Player Equivalence — what the player sees, hears, and controls (level/area, stars/coins/health/lives, Mario's action and sub-pixel position, Lakitu camera, whole-frame video within tolerance or an accepted visual variant, and audio SNR) — while enforcing Hyrum's Law on 1996 gameplay quirks: fixing C/memory undefined behavior is welcome, whereas changing quarter-step physics, wall-kick timing, or backwards long jumps fails the gate.

Headline console score + five hardware diagnostics

The headline leaderboard profile is console: per-frame max(CPU_ms, RSP_ms, RDP_ms) bottleneck time within the 4 MB retail RDRAM limit, reported both as bounded RLVR reward and unbounded est_fps / speedup. Five diagnostic profiles (speed, rdp, rsp, traffic, and memory) decompose every submission across each N64 subsystem with cross-budgets preventing pathological resource trades.

The 24-hour agent sandbox

The agent works inside mario-eval-task with the source tree, pinned compilers, n64run, mev check (restricted to public routes), and mev profile (clock-weighted PC sampling where cache-miss stalls land on the exact instruction that missed). Read-only task docs and locked git hooks prevent tampering, network egress is default-deny except model API endpoints, and held-out courses stay strictly on the host for checkpoint and final grading.

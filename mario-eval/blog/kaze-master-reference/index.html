The Kaze master reference: what an expert does with SM64

2026-11-20

The question this eval asks is how much cheaper Super Mario 64 can run on the original Nintendo 64 when it is engineered well for that hardware, while the player gets exactly the same game. To judge an agent's answer we need a human one. Kaze Emanuar has spent years doing this work and explaining it on video. The new calibration rung r10-kaze-master is our attempt to put all of it into vanilla SM64: every technique from his public videos and code that keeps the game the same, and nothing of our own.

How it was built

No single copy of Kaze's work exists. His two code downloads each serve one video: the repository for "How Optimizations made Mario 64 SLOWER" is cut down from his own mod, and the audio code from "Revolutionizing N64 programming!" says it was "not designed to work with the vanilla decomp repo". So we went to the videos: all 403 on his channel were transcribed, the source code he shows on screen in 44 technical videos was read frame by frame (about 440 frames), and each technique was checked against our tree and classified:

  • A: the output is bit-identical, so it goes in;
  • B: a visual change Kaze ships and considers no worse, which goes in only as a published, precomputed accepted variant (no LOD, full-detail Mario, F3DEX2, reduced-aliasing opaque modes, Rainbow Ride decoration baked into the level);
  • C: it changes gameplay or audio, or only applies to his own engine and assets, so it stays out.

Every change was measured on the six public courses and kept only if it helped, the "performance lottery" Kaze describes. The transcripts and frames are his content and are not in the repository.

Geometric mean 1.68× on the console model (reward 0.188), every gate passing. GCC -O2 alone gives 1.40×. The largest single steps were compiling the renderer, math, collision and audio code for size so each frame's working set fits the 16 KB instruction cache, linking the audio thread's per-update code contiguously, vertical object culling, and baking Rainbow Ride's 14 decoration pieces into the level.

What did not make it

  • Changes the game. One-raycast walls remove wall kicks; the folded-polynomial sine, the fast inverse square root and the rational atan2 give different numbers than vanilla, so physics drifts; his rewritten sound engine drops script features.
  • Depends on his engine. Removing the duplicate sample DMA buffers from "Mario 64 wastes SO MUCH MEMORY" broke playback here (audio fell to about −6 dB SNR): vanilla's sample loader relies on them, and his own ADPCM engine replaced that code.
  • Measured slower here. A reserved register for the current object (21 KB smaller code, 2% slower), a hand-written node dispatch table, inlining the fused matrix builder, and several cache-instruction tricks were neutral or worse on these routes.
  • Waiting on a ruling. Turning dithering off (about 15% of frame time in one of Kaze's scenes, but he calls it a matter of taste), one-matrix shadows, and re-exported actor rigs change how things look.

What the work changed in the grader

Building an expert reference is a good audit. Along the way:

  • The clock units were wrong and the CPU, RSP and RDP were summed. Now each frame costs its busiest unit, the CPU pays for waiting on the shared memory bus, and that one constant was fitted to Kaze's real-hardware frame rates for vanilla JRB, DDD and RR.
  • Accepted visual variants used to be single changes, so a submission combining two failed. Now every combination is precomputed (31 of them), and a change can be scoped to the course it affects.
  • The emulator charged nothing for CPU memory accesses that bypass the caches, so mapping hot data uncached would have skipped every cache-miss charge. They now cost what a cache fill costs.
  • The reward is now log2(speedup)/4: each doubling is worth the same, with no ceiling.

Beyond Kaze

r11-beyond-kaze adds work Kaze never described: object fields ordered so each frame's hot fields share 16-byte D-cache lines, skipped stores of unchanged values, an audio struct reorder, and double buffering. It exists to check that the reward keeps climbing past the human reference, which is where a strong agent should end up.

Known gap: Jolly Roger Bay cannot reach 60 FPS without changing the picture. Its translucent fog plane over the water costs about 4 ms of RDP time on its own; Kaze calls it "the main reason why this level has such poor frame rates". The rules keep it, because removing it changes what the player sees.

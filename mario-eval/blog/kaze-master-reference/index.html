The Kaze master reference: what an expert does with SM64

ILYAAS KAPADIA · 2026-11-25

The question this eval asks is how much cheaper Super Mario 64 can run on the original Nintendo 64 when it is engineered well for that hardware, while the player gets exactly the same game. To judge an agent's answer we need a human one. Kaze Emanuar has spent years doing this work and explaining it on video. The new calibration rung r10-kaze-master reconstructs applicable techniques from his public videos and code on vanilla SM64. It is not Kaze's engine or a complete port of his work.

How it was built

No single copy of Kaze's work exists. His two code downloads each serve one video: the repository for "How Optimizations made Mario 64 SLOWER" is cut down from his own mod, and the audio code from "Revolutionizing N64 programming!" says it was "not designed to work with the vanilla decomp repo". We collected captions or ran speech recognition across the 424-video channel inventory. 309 videos yielded timestamped speech; 115 produced no transcript text. We searched the transcripts for techniques, reviewed extracted code frames from technical videos, and recovered clues from release descriptions and silent demos. An empty transcript does not establish that a video has no technical content.

We classified the techniques we found:

  • A: a candidate that preserves output, subject to verification and measurement;
  • B: a visual change Kaze ships and considers no worse, which goes in only as a published, precomputed accepted variant (no LOD, full-detail Mario, F3DEX2, reduced-aliasing opaque modes, Rainbow Ride decoration baked into the level);
  • C: it changes gameplay or audio, or only applies to his own engine and assets, so it stays out.

Every change was measured on the six public courses and kept only if it helped, the "performance lottery" Kaze describes. The transcripts and frames are his content and are not in the repository.

Geometric mean 1.73× on the console model (1.25× over GCC -O2, reward 0.198; 1.69× across all 25 public + held-out + button-mash routes, PLAY=1 runtime smoke passing), every gate passing. GCC -O2 alone gives 1.38×. The largest single steps were compiling the renderer, math, collision and audio code for size so each frame's working set fits the 16 KB instruction cache, switching from Fast3D to F3DEX2 (breaking the Fast3D RSP wall on BoB and RR), linking the audio thread's per-update code contiguously, vertical object culling (with a 1,200-unit vertical margin so tall level objects such as Wet-Dry World elevators do not pop out), reduced-aliasing opaque modes (cutting RDP fillrate and RDRAM bus contention), and baking Rainbow Ride's 14 decoration pieces into the level.

The follow-up pass removed unused engine command bodies and shared audio-bank relocation code. Branch hints did not move the score; rolling more matrix functions saved code space but ran slower on these routes.

Correction (2026-11-21). This reference was first published at 1.69×. Seeded button mashing, added to the held-out routes, then showed it was not the same game. Its table-free sine and cosine were within one unit in the last place of vanilla's table, not equal: 1,803 of 4,096 entries differed, which moved Mario, the camera and sound panning (a 1.8-unit camera jump in Rainbow Ride, changed audio in Bob-omb Battlefield). And vertical culling skipped drawing objects whose drawing code moves other objects, freezing the sushi sharks' collision helpers in Dire Dire Docks. Both passed the old gate's tolerances on the six scripted routes. The fixes are a 512-byte map that corrects the 901 polynomial results that differ, and keeping the vanilla test for objects that move others when drawn. Gameplay and audio are now bit-identical to vanilla on the public routes and on mashing (Rainbow Ride's accepted decoration variant itself shifts 54 audio samples), at a cost of about 2%. The gameplay gate now also checks every object within 2,000 units of Mario.

Every remaining technique, measured (2026-11-21). We then tried each remaining Kaze and ultrasm64 technique as its own change on top of this reference: about 60 trials, each timed at seven code layouts and checked for exact gameplay and audio on the public routes plus 24 seeded button-mashing runs. Four were exact and faster on every layout and are now in: compiling the N64 system library for size (r10's libultra flags only applied to the IDO compiler), Kaze's 4×3 matrices with shared rotation products, an exact flat-floor shortcut in collision from FazanaJ's fork, and overlapping the framebuffers' unused border rows (10 KB of RAM). Together they lifted the reference to 1.67× under the updated hardware cost model (adding 4-bank × 2 KB RDP RDRAM page-miss penalties, hardware early-Z write rejection, bus-coupled CPU contention proportional to concurrent RCP traffic, and 60 Hz VI scanout at sustained 250 MB/s). Under that model, Fast3D hits an active RSP wall on BoB and RR as soon as CPU time drops, and JRB flips to RDP-bound at r10-kaze-master (58%+ once D-cache layout is optimized further). Expanding the held-out suite with Hazy Maze Cave and Wet-Dry World also caught a tall-object vertical culling pop-in on mash-wdw, fixed with a conservative 1,200-unit vertical margin so r10-kaze-master passes all 25 routes cleanly.

Final Kaze & ultrasm64 completion pass (2026-11-22). After auditing all 424 videos, both Kaze code releases, and both ultrasm64 forks against the v2 cost model, we tested the remaining 8 unimplemented techniques individually and across 5 code-layout pads. Five were exact and layout-independently faster (median +2.71%, range [+1.48%, +3.12%] across pads): Kaze's targeted osWritebackDCache flush in main.c (with explicit &lookAt and Goddard title-screen flushes), KSEG0- and 16-byte-guarded cache 0x0d (Create Dirty Exclusive) in bzero.s and bcopy.s (cache_uncached_ops == 0), Kaze's exact find_floor_height shadow lookup, FazanaJ's hoisted gSPLookAt, and FazanaJ's above-camera shadow cull. The PLAY=1 runtime smoke test also caught a real N64 boot hang in the prior r10 build: lazy object-pool clearing left gObjParentGraphNode.children == NULL in the 0-object intro level, causing load_obj_warp_nodes() to loop indefinitely until guarded. Together these lifted r10-kaze-master to 1.73× on the 6 public routes (1.25× vs GCC -O2) and 1.69× across all 25 private routes — faster on 25 of 25 routes with zero gate or coherence regressions. Meanwhile FRUSTRATIO_2 cut RSP cycles by 13.7% but failed the strict 0.20% video gate (0.23% on 3 frames), and -Os on hot game-loop TUs regressed console speed by 3.53%. The full per-technique record is r10-trials.md.

What did not make it

  • Changes the game. One-raycast walls remove wall kicks; the fast inverse square root gives different numbers than vanilla, so physics drifts; his rewritten sound engine drops script features. His polynomial sine and atan2 are in, corrected to return vanilla's exact table values.
  • Depends on his engine. Removing the duplicate sample DMA buffers from "Mario 64 wastes SO MUCH MEMORY" broke playback here (audio fell to about −6 dB SNR): vanilla's sample loader relies on them, and his own ADPCM engine replaced that code.
  • Audio opcode pruning stays out. The decoder processed all 34 binary retail sequence streams, but 19 still contain raw opcode-range bytes it cannot classify. The six course replays do not test every menu, cutscene, or credits sequence. The reference shares audio-bank relocation code instead of deleting handlers.
  • Measured slower here. A reserved register for the current object (21 KB smaller code, 2% slower), a hand-written node dispatch table, inlining the fused matrix builder, and several cache-instruction tricks were neutral or worse on these routes.
  • Waiting on a ruling. Turning dithering off (about 15% of frame time in one of Kaze's scenes, but he calls it a matter of taste), one-matrix shadows, and re-exported actor rigs change how things look.

What the work changed in the grader

Building an expert reference is a good audit. Along the way:

  • The clock units were wrong and the CPU, RSP and RDP were summed. Now each frame costs its busiest unit, the CPU pays for waiting on the shared memory bus, and that one constant was fitted to Kaze's real-hardware frame rates for vanilla JRB, DDD and RR.
  • Accepted visual variants used to be single changes, so a submission combining two failed. Now every combination is precomputed (31 of them), and a change can be scoped to the course it affects.
  • The emulator charged nothing for CPU memory accesses that bypass the caches, so mapping hot data uncached would have skipped every cache-miss charge. They now cost what a cache fill costs.
  • The reward is now log2(speedup)/4: each doubling is worth the same, with no ceiling.

Beyond Kaze & v3.1 Symmetric RDP Update (2026-11-25)

Under the v3.1 symmetric RDRAM bus model (which charges RDP 32-byte DP_DMA/DP_DRAW burst turnarounds alongside CPU cache-miss contention, plus GBA-Eval 16×16 block-SSIM, log-mel audio, and active PLAY=1 RSP audio verification), we re-audited 24 additional Kaze trials and folded seven clean, vanilla-preserving wins into r10-kaze-master: deduplicating the redundant gGfxPool->buffer writeback in writeback_sp_task, a 9-TU sequence_unity.c audio unity build, outlining geo_finish_transform's tail, skipping redundant Mario LOD nodes, Kaze's single-raycast planar shadow projection, early-Z draw ordering on Bob-omb Battlefield's ground mesh, and inline gSP2Triangles skybox quads. Across all 25 public + private + button-mash routes, r10-kaze-master scores 1.663× (39.9% console frame time saved, 1.238× over GCC -O2's 1.343×, and 2.043× graphics RSP speedup).

r11-beyond-kaze was also rebuilt cleanly on top of r10-kaze-master (fixing an earlier prototype that had renumbered object_fields.h slots and compiled hot TUs with -Os): packing named struct Object members onto 16-byte D-cache lines, skipping unchanged header.gfx.pos/angle and collision stores on stationary objects so D-cache lines stay clean, and unpacking 1-bit audio channel bitfields into bytes lifts 25-route performance to 1.697× (41.1% console frame time saved, 1.263× vs GCC -O2, 1.780× CPU).

Jolly Roger Bay was still above the 16.7 ms budget for 60 FPS in this build. Its translucent fog plane over the water costs about 4 ms of modeled RDP time on its own. Removing it changes what the player sees, so the reference keeps it.

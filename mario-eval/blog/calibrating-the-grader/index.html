Calibrating the grader

2026-11-15

A reward function for RL has to be right about cases you already understand before it can be trusted on cases you don't. So before any model touches Mario Eval, I wrote fifteen patches against the baseline whose outcomes I could predict, and graded each one exactly like a submission, on four public and four held-out routes. The full numbers are on the calibration page; this post is about what they showed, including one result I had wrong the first time.

The shortcuts all fail, and fail early

Six patches make the game cheaper by changing it. All six score −1, and the grader names the first thing that went wrong:

  • Muting the synthesizer is caught by the gameplay gate before the audio gate: the voice count in the observation record differs on frame 9, because voices that never decay are never freed. The audio gate then reports 0 dB SNR.
  • Two physics substeps instead of four changes Pip's height on frame 1.
  • Not drawing particles passes every gameplay check (particles still exist; they're just invisible) and is caught by video alone: 1.0% to 4.8% of pixels fail on the worst frame of each route, against a 0.2% limit.
  • Always drawing Pip at his lowest detail is caught by video too: 0.54% to 0.69% of pixels.
  • -O2 with fast-math, libdragon's default, is the interesting one. It is the most natural first move for an agent, it halves frame time, and it fails: on frame 54 of the meadow route, Pip's x-velocity is 0.393291771 instead of 0.393291712. Fast-math lets the compiler reorder and contract floating-point expressions, and one rounding difference in the simulation eventually becomes a different game. The same flags with -fno-fast-math are valid and score 0.498.
  • Editing the harness is caught by a hash before anything is built.

Accepted visual changes

"The picture must match" is too strict for the changes this eval is named after. Kaze Emanuar's SM64 optimizations draw Mario at full detail all the time instead of switching to lower-detail models as the camera pulls back: faster on his engine, and arguably better looking. That should be rewarded, so the grader keeps a short, published list of accepted visual changes. Each is a patch to the original game. When the reference is recorded, the grader applies it, refuses it unless gameplay and audio stay bit-for-bit identical, and keeps its picture as a second reference. A submission's pixel passes if it matches the original or an accepted variant.

To test it, Pip got Mario-style detail levels: he drops his visor, then his head, when the camera is far away. Always drawing him at full detail is now valid (it passes video on every route), and always drawing him at his lowest detail still fails. The list is the policy; anything not on it has to match the original picture.

Tolerances, set from both sides

Gameplay is compared bit for bit, but the picture and the sound can't be: a legitimate change to how a vertex is computed can move an edge by a fraction of a pixel. Reassociating one matrix product, (P·V)·M instead of P·(V·M), changed at most 0.001% of the pixels on any frame. Replacing sinf with an interpolated table and the asinf(sinf(x)) triangle wave with its closed form left the audio at 88 to 91 dB SNR, and no frame below 67 dB.

The limits (0.2% of pixels with a one-pixel neighbourhood and 2/31 per channel; 40 dB overall and 20 dB per frame) sit between the two sides. Audio has an enormous margin. Video has less than I'd like: the smallest shortcut failure is the low-detail patch at 0.54% of pixels, under three times the limit. A shortcut that removes something small and rare could slip under it, which is an argument for more routes and for gameplay-level checks of everything that's drawn, not for loosening anything.

The performance lottery, and a result I got wrong

The N64's data cache is 8 KB and direct-mapped: two addresses 8 KB apart share a line. Moving data by a few hundred bytes can make hot buffers evict each other, or stop doing so. Calibration ran into this three ways:

  • Two ways to force full detail. Replacing Pip's distance check with a constant deleted 208 bytes of code. Every piece of data after it moved down 208 bytes while the stack and heap stayed put, data-cache misses rose from about 6,800 to 28,700 per frame on one route, and the game got 17.8% slower. Forcing the same result in a way that deleted 112 bytes cost 0.2%. Same picture, same work, very different score, and the grader is right both times: the console's cache is direct-mapped too.
  • Create Dirty Exclusive. The CDE patch claims each line of the synthesizer's 2 KB output block with cache 0x0d so the cache doesn't read stale samples it is about to overwrite. In my first calibration run it scored +0.043 on speed, with data-cache misses on one route falling from 15,532 to 4,831 per frame. That was wrong to credit to CDE: 2 KB is 128 cache lines, so CDE can save at most 128 fills per frame. The rest was the layout lottery. After the baseline gained the detail-level code and everything shifted, the same patch saves its 128 fills and scores −0.008, because its extra instructions moved code into worse I-cache positions. CDE pays off when a large buffer is overwritten often; here the buffer is too small to beat layout noise.
  • Budgets. Precomputing the terrain's heights is 10% faster and fails the memory profile: the table is 448 bytes the original didn't need. The sine table is 8.6% faster and fails it too.

None of these are grader bugs; they're the N64's costs being what they are. But it does mean single-patch rewards on a small game are noisy around zero, and an agent that only reorders code can win or lose a few percent by luck. Two things follow. Calibration claims should rest on patches whose effect is much larger than layout noise (-O2 at +0.498, the memory patch at +0.408). And an agent that wants a reliable score has to control layout deliberately, as N64 developers do, rather than hope for it.

What calibration doesn't prove

Every number here is from the ares model of the N64, which does not time the RDP or model bus contention (see what the emulator measures). The rankings above are about CPU, RSP, traffic and memory as ares counts them. The next calibration step is the same fifteen ROMs on a console, and then the same exercise on Super Mario 64.

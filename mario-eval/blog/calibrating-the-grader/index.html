Calibrating the grader

2026-11-14

A reward function for RL has to be right about cases you already understand before it can be trusted on cases you don't. So before any model touches Mario Eval, I wrote twelve patches against the baseline whose outcomes I could predict, and graded each one exactly like a submission, on four public and four held-out routes. The full numbers are on the calibration page; this post is about what they showed.

The shortcuts all fail, and fail early

Five patches make the game cheaper by changing it. All five score −1, and the grader names the first thing that went wrong:

  • Muting the synthesizer is caught by the gameplay gate before the audio gate: the voice count in the observation record differs on frame 9, because voices that never decay are never freed. The audio gate then reports 0 dB SNR.
  • Two physics substeps instead of four changes Pip's height on frame 1.
  • Not drawing particles passes every gameplay check (particles still exist; they're just invisible) and is caught by video alone: 1.0% to 4.8% of pixels fail on the worst frame of each route, against a 0.2% limit.
  • -O2 with fast-math, libdragon's default, is the interesting one. It is the most natural first move for an agent, it halves frame time, and it fails: on frame 54 of the meadow route, Pip's x-velocity is 0.393291771 instead of 0.393291712. Fast-math lets the compiler reorder and contract floating-point expressions, and one rounding difference in the simulation eventually becomes a different game. The same flags with -fno-fast-math are valid and score 0.496.
  • Editing the harness is caught by a hash before anything is built.

Tolerances, set from both sides

Gameplay is compared bit for bit, but the picture and the sound can't be: a legitimate change to how a vertex is computed can move an edge by a fraction of a pixel. Two probes measure how much legitimate noise there is. Reassociating one matrix product, (P·V)·M instead of P·(V·M), changed at most 0.001% of the pixels on any frame. Replacing sinf with an interpolated table and the asinf(sinf(x)) triangle wave with its closed form left the audio at 88 to 91 dB SNR, and no frame below 67 dB.

The limits (0.2% of pixels with a one-pixel neighbourhood and 2/31 per channel; 40 dB overall and 20 dB per frame) sit between the two sides. Audio has an enormous margin. Video has less than I'd like: the smallest shortcut failure is a fortress route where only 0.97% of pixels change, five times the limit. A shortcut that removes something small and rare could slip under it, which is an argument for more routes and for gameplay-level checks of everything that's drawn, not for loosening anything.

The CACHE instruction, measured

The Create Dirty Exclusive patch is four lines: before the synthesizer fills its 2 KB output block, claim each 16-byte line with cache 0x0d, so the data cache doesn't read 2 KB of stale samples from RDRAM only to overwrite them. On the concert route, the most audio-heavy, data-cache misses fell from 15,532 to 4,831 per frame and D-cache traffic from 346 KB to 86 KB per frame, and frame time fell 8.6%. Overall: +0.043 on speed, +0.108 on traffic. It is a small, real, hardware-specific win, which is exactly what the eval is meant to reward, and the emulator models it faithfully enough to see it.

Budgets are where the surprises are

Each task scores one resource and treats the others as budgets. That's where calibration found things I hadn't predicted:

  • The sine table is 5% faster and moves 32% more data on one route. Not because of the table: the new code shifted the layout, and hot functions started evicting each other from the direct-mapped instruction cache. It's valid for speed and rejected for traffic.
  • The reassociated product costs nothing in time and still raises traffic 7.8% on one route, by the same mechanism.
  • The engine patch (view-projection once per frame, terrain heights precomputed) is a clear speed win and is rejected for memory: the height table is 324 bytes the baseline didn't have.

None of these are grader bugs. They're the N64's costs being what they are, and the reason a single combined score would be misleading. An agent asked to reduce traffic has to manage code layout as well as algorithms; one asked to reduce RAM can't spend it on tables.

What calibration doesn't prove

Every number here is from the ares model of the N64, which does not time the RDP or model bus contention (see what the emulator measures). The rankings above are about CPU, RSP, traffic and memory as ares counts them. The next calibration step is the same twelve ROMs on a console.

Models try to make Super Mario 64 run faster on a real Nintendo 64.

We give AI coding agents the C source of Super Mario 64, N64 hardware specs, and 24 hours to make it run as fast as possible on an original 4 MB console, without changing the game. Every frame is costed on an instrumented N64 emulator and checked against the 1996 game.

The 1996 build runs at about 37 uncapped frames per second on our routes (well shy of the N64's 60 Hz refresh ceiling). There is no score cap: agents push console FPS and speedup as high as the 4 MB hardware allows.

Scoring

After 24 hours we rebuild the agent's game from source with our own toolchain and replay recorded controller input on 26 routes: the 6 public courses the agent can test, plus 20 private routes it never sees (other courses and seeded button mashing). A frame costs as much as the busiest of the console's four units, which run in parallel: max(CPU, RSP, RDP, RDRAM bus). See What the emulator measures and Calibrating the grader.

Speedup, FPS & RL rewardscore

In Mario Eval v4, the 6 public dev courses carry 0% weight in the final score — 100% of the score comes from unseen private held-out trajectories (75% scripted multi-course/multi-act routes, 25% seeded random-input routes across 18 SM64 worlds). We report unbounded speedup (1 / geomean(Tcand / T1996)) and uncapped console FPS alongside log-scaled RL reward (log2(speedup) / 4) and bounded cycle cost saved 1 − Tcand / T1996 ∈ [0%, 100%).

Diagnostic sub-rulerstelemetry

Every run automatically reports per-route effective speedup, held-out generalization, public-only overfit drift, 24h working-tree retention (final / peak), and numerical failure attribution (VR4300 CPU ISA traps, 4 MB RDRAM OOB, cache/DMA UB, PLAY=1 divergence, actor desync, video/audio regressions) without reading transcripts.

Gameplaygate

Mario's position, speed, action and stats, the camera, and every actor within 2000 units match the 1996 game on every frame.

Videogate

Each frame matches the original picture, or one consistent accepted variant (such as Nintendo's F3DEX2 microcode) across the replay, on 99.8% of pixels within ±2/31 per channel and ≥ 0.98 single-scale 16×16 block-SSIM.

Audiogate

At least 40 dB signal-to-noise against the original sound output, or a perceptual 40-band log-mel spectrogram match (≥ 0.95 cosine similarity on both stereo channels, loudness-guarded) for timing-preserving audio rewrites.

Hardwaregate

Fits in 4 MB of RAM with zero unaligned CACHE 0x0d ops, zero KSEG1 dirty-cache synonyms, coherent SP/DP DMA writebacks, untouched harness/PLAY glue, and a linked PLAY=1 retail console ROM that cold-boots with active video and RSP audio. No route may regress > 5%. Failing any gate scores −1.

How models run

Each model gets a Docker container with the Super Mario 64 decompilation (extracted assets, no ROM), the SGI IDO and GCC MIPS compilers, the instrumented emulator, and a mev tool that builds, runs, profiles and grades the public courses. It has no internet access beyond its model API. We run each model for 24 hours; the host commits its work and grades a snapshot on every route every two hours.

See Building Mario Eval for the container layout and the task statement.

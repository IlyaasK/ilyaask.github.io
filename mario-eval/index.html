MARIOEVAL
Overview Calibration Blog GitHub

Make a Nintendo 64 game cheaper to run. Don't change it.

Mario Eval is a reinforcement-learning-with-verifiable-rewards environment. An agent gets the source of an N64 game, a toolchain, an emulator and a profiler, and has to cut what the game costs on the original hardware — CPU time, RSP time, memory traffic or RAM — while every frame of gameplay, picture and sound stays the same. The reward comes from measurements, not from a judge.

Status: the environment, grader and agent container are built and calibrated on Pip's Garden, an original stand-in game written for this eval (the robot above). Super Mario 64 plugs into the same harness once a legally dumped ROM is supplied; see the road to Super Mario 64. No models have been run yet.

How a submission is graded

The grader rebuilds the submitted source with a pinned toolchain, then runs it in ares (CPU interpreter, so the VR4300's instruction and data caches apply to every instruction) with a small instrumentation patch. Recorded controller inputs are fed per logical game frame, and the game runs unthrottled, so a faster build plays exactly the same game. Every cost is counted by the emulator; nothing the ROM says about itself is trusted.

speed

CPU time per frame (COUNT ticks), including every cache stall.

rsp

Vector-coprocessor busy cycles per frame.

traffic

RDRAM bytes moved per frame by every bus device.

memory

Distinct RDRAM bytes the game touches after boot.

A task names one profile. Reward = 1 − the geometric mean over workloads of candidate cost / baseline cost, clipped to [−1, 1]: halving the cost scores 0.5. A submission that fails any gate scores −1 on every profile, however fast it is. Non-speed profiles also carry a frame-time budget, so RAM can't be bought with time.

What must not change

  • Gameplay: the observation record (player, camera, enemies, gems, RNG state, ...) must match the original bit for bit on all 240 frames of every route.
  • Video: a pixel passes if a pixel within one pixel of it in the original frame is within 2/31 per channel; a frame fails above 0.2% failing pixels. Sub-pixel edge shifts pass; missing objects don't. Accepted visual changes judged equal or better looking, like Kaze's always-full-detail Mario, also pass: each is a published patch to the original, verified to leave gameplay and audio identical, and its picture counts as a second reference.
  • Audio: ≥ 40 dB SNR overall, ≥ 20 dB on every non-silent frame.
  • Harness and hardware: the harness files are byte-identical; the game fits a 4 MB console.

The baseline

Run it

git clone https://github.com/IlyaasK/mario-eval && cd mario-eval
scripts/build-images.sh --no-task          # toolchain, ares + n64run, grader
scripts/precompute.sh                      # baseline reference
scripts/grade.sh path/to/your/game out/    # grade a source tree
scripts/build-images.sh && cd quickstart && docker compose up -d   # agent container

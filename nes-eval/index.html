NES Eval

An AI coding agent gets an empty Rust project, the NES hardware documentation and a black-box reference emulator, and has 24 hours to write an NES emulator that compiles to WebAssembly. The emulator is then run in lockstep with the reference on 23 test ROMs and 6 recorded homebrew playthroughs, and every one of 44,980 frames of picture and sound is compared.

It is a port of Mechanize's GBA Eval to a different console. The grader and metrics are theirs; the reference (RustyNES), the ABI, the corpus and the agent environment are new, and so are the problems the NES raised. How the port works · Did any model hack the grader?

How it is graded

overall = 0.60 × replay + 0.20 × procedural + 0.20 × audio, GBA Eval's weights.

60%

Replay

Six homebrew games, 5,400–6,000 frames each, driven by recorded button presses. Every frame is compared with block SSIM; one frame of timing drift desynchronises the whole playthrough.

20%

Procedural

23 self-checking test ROMs (blargg, kevtris's nestest, Holy Mapperel) for the CPU, PPU, APU and mappers, scored on their final verdict screen.

20%

Audio

Per-frame log-mel spectral distance against the reference's PCM, on the four APU mixer tests and all six games.

Candidates hand over 9-bit palette indices rather than RGB, so a different colour palette cannot cost points, and the power-on state is pinned in the ABI so a correct emulator can match the reference exactly. Full rubric: README; per-testcase scores: Results.

  • 2026-10-16Did any model hack the grader?

    Four models, 24 hours each. No model special-cased a test ROM, but one constant fitted to the reference is worth 0.36 of a score, one model worked out which emulator it was graded against, and the harness itself had a bug that ended a run early.
